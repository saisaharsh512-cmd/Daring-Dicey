# Daring Dicey — full stack

Everything needed to run the app end to end:

```
daring-dicey/
├── frontend/   Daring Dicey-branded React app (Vite) — talks to the backend over HTTP
└── backend/    FastAPI service — image gating, damage detection models, scoring,
                evacuation planning, incident report generation
```

This is your original `disaster-response-dashboard` backend (unchanged, source
only — its `.venv` and `__pycache__` folders were stripped out since they're
regenerated by `pip install`) paired with the re-themed frontend built from
your `dicey-fixed` branding.

## 1. Start the backend

```bash
cd backend
pip install -r requirements.txt
export LLM_API_KEY=your_key      # optional — narrative reports fall back to
                                  # deterministic text without it
uvicorn api.server:app --reload --port 8000
```

Notes:
- `torch`, `ultralytics`, and `transformers` are heavy installs; first run
  will also download several model weights (YOLO detectors + CLIP), so the
  first request will be slow.
- No API key is required for the core pipeline (detection, severity,
  evacuation planning) — only the LLM-narrated incident report needs one.

## 2. Start the frontend

```bash
cd frontend
npm install
cp .env.example .env    # already points at http://localhost:8000
npm run dev
```

Open the printed local URL. The topbar status pill shows CONNECTING →
SYSTEMS ONLINE once it can reach the backend.

## 3. Use it

1. Pick a disaster type.
2. Upload site images (drag-drop or browse).
3. Switch to the **Map** tab and click a location for each uploaded image
   (this geotags it — required before you can analyze).
4. Hit **ANALYZE DISASTER**.
5. Results populate across the tabs: Overview, Hazard Analysis, Map,
   Evacuation, Recommendations, Incident Report, Model Status.

## What changed from your original two folders

- **Frontend** is the working app from `disaster-response-dashboard`

## Rescue Team Allocation
The UI accepts a total available rescue-member pool. After analysis, the backend creates bounded teams for disaster-confirmed locations by severity/priority and reports allocated versus reserve personnel. The pool is never automatically deployed in full to a single location.

## Evacuation routing

After a disaster analysis, open the **Evacuation** tab. Select a disaster-confirmed affected location, enter a responder-verified safe-zone/shelter coordinate, and calculate a road-network route. The UI displays the route, distance, and estimated driving time on a Leaflet map.

The backend uses OSRM by default (`https://router.project-osrm.org`). Set `OSRM_BASE_URL` to point at a self-hosted routing service if desired. Routing is not a live safety guarantee: it does not know current road closures, flooding, fire lines, traffic, or emergency restrictions, so routes must be verified locally before evacuation.
